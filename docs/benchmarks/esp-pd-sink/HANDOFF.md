# Foilfern — ускорение подготовки routing candidates

Главный результат этой задачи — коммит с изменением Rust-кода Foilfern,
который устраняет воспроизводимую проблему подготовки или анализа
кандидатов. ESP‑PD‑Sink используется как вход для проверки патча.
Начни с замера на release. Новая разводка платы, перебор размещений и
производственный экспорт отложены до отдельной задачи.

## Что продолжаем

Текущий этап работы над роутингом начался с единого routing service:
проверяемые кандидаты, preview и атомарные apply/undo. На ESP‑PD‑Sink и ESP32‑C3
мы уже добавили диагностику потерянных связей через заливки (`803beb1`),
правку отвергнутого кандидата без его применения (`8007a6f`), замену
via (`f3aa355`), дельту связности по каждой цепи (`dff33c9`) и перенос
компонента вместе с локальной правкой меди (`e63f109`). Повтор на
двухслойной ESP32‑C3 закрыл все шесть оставшихся разрывов (`c7df48a`).
Следующая задача продолжает этот цикл в продукте: воспроизвести
затруднение одной MCP-операцией, исправить его в коде и проверить на
той же плате. [Roadmap и критерии проверки](../../roadmap.md).

## Что уже измерено

Облачная ветка `work` сохранила результаты эксперимента в
[отчёте ESP‑PD‑Sink](https://github.com/okhsunrog/foilfern/blob/c331f1761ad1bb1ccae634c72add04fe79beea9b/docs/benchmarks/esp-pd-sink/review/REPORT.md).
На локальной операции OLED `prepare` занял 29,91 с, из них 14,83 с
заняла исходная DRC и 14,08 с — DRC кандидата. `preview` занял 4 мс,
`apply` — 13,42 с. В локальном опыте builtin исходная и итоговая DRC
вместе заняли 27,80 с из 29,18 с подготовки. Эти прогоны сделаны на
dev-сборке с `opt-level=2` для core, clipper, editor и autoroute.
Полный DRC на обычной dev-сборке занял 78,30 с. Замера release пока
нет. Сам поиск в этом опыте делал один запрос без rip-up.

## Порядок работы

1. Собери Foilfern в release по инструкции ниже и возьми сохранённый запрос
   `evidence/oled-rotate-both-0-input.json` из архива или проверенный
   [OLED-запрос из ветки work](https://github.com/okhsunrog/foilfern/blob/c331f1761ad1bb1ccae634c72add04fe79beea9b/docs/benchmarks/esp-pd-sink/review/candidates/oled.json).
   В одном процессе MCP повтори `prepare → discard` на той же плате
   и ревизии. Сними время первого и повторного вызова и долю исходной
   DRC. Сохрани запрос, профиль и параметры сборки для сравнения
   с патчем.
2. Если release подтверждает, что существенная доля времени уходит
   на повторную исходную DRC, измени `librepcb-editor`, чтобы повторная
   подготовка переиспользовала исходный результат DRC для того же снимка.
   Начни с `RoutingService`, `RoutingJob::run` и
   `capture_routing_state`. Проверь, какие данные проверок нужны самому
   поиску. Если кеширование исходной проверки в текущей архитектуре
   требует большого рефакторинга, профилируй конкретные этапы DRC и
   реализуй более узкое устранение повторной работы с замером. Если
   release уже снимает проблему и профиль не выявляет другой явной
   задержки, реализуй описанный ниже read-only MCP замер длины пути
   между площадками. Он устраняет необходимость вручную собирать
   сегменты для ревью OLED и U5.
3. Для переиспользования DRC сохрани границы корректности. Результат
   применим для той же
   сессии проекта, платы, ревизии и контекста, влияющего на расчёт,
   включая путь, сохранение и атрибуты физических надписей. Новые ошибки
   DRC и разрывы от перестройки GND должны выявляться по-прежнему.
   Проверь переходы между ревизиями, платами и сессиями. Итоговая
   проверка кандидата и проверка после применения остаются свежими.
4. Закоммить реализацию и запушь ветку задачи. Приложи команды
   воспроизведения и целевые тесты. Для патча производительности укажи
   время первого и повторного `prepare` до/после и результаты DRC и
   связности. Для MCP-замера приложи запрос, результат и проверку
   на сохранённой паре выводов из ESP‑PD‑Sink.
   Документация, архивы, изменения PCB и скрипты вне продукта сами
   по себе этот этап не закрывают.
5. После первого проверенного коммита профилируй builtin на одном
   ограниченном участке с конкурирующими трассами. Если заметную долю
   времени съедает поиск, реализуй и измерь одно ускорение. Сравни
   оставшиеся разрывы, DRC, длину трасс и число via при тех же входных
   данных. Если MCP-замер пути ещё не сделан, перенеси расчёт между
   площадками из прототипа в read-only MCP API с идентификаторами платы
   и ревизии. Покажи длину, слои, via и явно сообщай об участках,
   проходящих через заливку, длина которых не измерена.
   [Прототип измерений и групп](https://github.com/okhsunrog/foilfern/blob/c331f1761ad1bb1ccae634c72add04fe79beea9b/docs/benchmarks/esp-pd-sink/review/README.md).

## Входные данные

- Оригинальный снимок платы снят на `c7df48a`. Работай от текущего
  `master`. Прочитай
  `AGENTS.md`, [рабочий процесс MCP](../../mcp-board-workflow.md) и
  [контракт routing candidates](../../mcp-design.md#reviewed-builtin-routing).
- Архив [inputs.tar.gz](inputs.tar.gz) содержит самодостаточный проект
  `foilfern/ESP-PD-Sink.lpp`, исходные файлы KiCad `kicad/esp-pd.kicad_*`
  из `5b96caf` ветки `epr-48v`, и каталог `evidence/` с замерами,
  исходными отчётами и примерами BOM. Разверни архив в рабочий каталог
  облачной задачи и открывай временную копию проекта для экспериментов.
- Собери MCP через
  `cargo build --locked --release -p librepcb-mcp --bin librepcb-mcp`
  и запусти `target/release/librepcb-mcp`.
  Если исходники upstream находятся вне `../LibrePCB`, укажи
  `LIBREPCB_UPSTREAM_DIR`. Для сборки нужен ресурс
  `share/librepcb/fontobene/newstroke.bene` из upstream. Сервер работает
  по stdio. Передай абсолютный путь через `--project` или открой копию
  инструментом `project_open`. Прогон через stdio-клиент подходит для
  облачной среды без GUI. Порядок работы описан в
  [руководстве Foilfern](../../mcp-board-workflow.md).
- Для регрессии зафиксируй исходное состояние. База имеет
  86 посадочных мест, 0 разрывов, 0 ERC, 3 ошибки DRC и 9 предупреждений.
  Две ошибки относятся к зазору медь–отверстие у J2, третья к
  `AE1:2` в keepout. Предупреждения касаются восьми щелей и радиуса
  контура. In1 служит опорной землёй. Исходные отчёты Foilfern и
  LibrePCB 2.1.1 лежат в архиве.
- Цель предыдущего прохода состояла в замыкании цепей на импортированном
  размещении. Сначала разводились силовые цепи, земля, USB и RF. Из 86
  координат и сторон посадки поменялась только координата C11,
  с `(116.25, -117.10)` на `(116.25, -118.50)` мм. Результат
  служит базой для сравнения качества размещения.

## BOM

Проблема `Package=N/A` в эксперименте ESP32-C3 воспроизведена. Вызов
`export_bom` без `board` создаёт BOM проекта и по контракту заполняет
`Package` как `N/A`. Передай имя платы из `board_get`.

```json
{"board": "default", "assembly_variant": "Std"}
```

На исходном проекте сравнения обе версии содержат 36 designator в
23 строках. В board BOM заполнены все корпуса. На ESP‑PD‑Sink board BOM
содержит 80 устанавливаемых позиций в 53 строках. C3, C31, R2, R7,
R26 и R28 отсутствуют в этой сборке. Пустые MPN и Manufacturer отражают
отсутствие заполненных закупочных данных. Для UX можно возвращать явный
scope и выбранную плату в ответе, сохраняя режим проекта.
