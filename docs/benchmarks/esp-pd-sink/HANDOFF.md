# ESP‑PD‑Sink — ревью размещения и локальная доработка

Задача для облачной сессии Foilfern. Возьми сохранённую четырёхслойную
ESP‑PD‑Sink и улучши размещение и разводку критичных узлов. Начни с
OLED и обратной связи DC/DC. Сравни варианты на копиях и сохрани
лучший проверенный проект вместе с отчётом. Оптимизируй и геометрию
трасс, и время работы роутера. Используй MCP для правок и фиксируй
ограничения, которых ему не хватает на этой плате.

Главная цель — улучшать сам Foilfern на препятствиях, обнаруженных при работе
с реальной платой. Для каждого программного ограничения сохраняй
воспроизводимый пример, исправляй реализацию или API, добавляй проверку
и повторяй исходную операцию. Изменения платы и внешние измерительные
скрипты служат материалом для этой работы. Сохраняй полноту DRC,
проверок связности и совместимость native-файлов при любых ускорениях.

## Входные данные

- Исходный код Foilfern на момент замеров: `c7df48a`. Прочитай
  `AGENTS.md`, [рабочий процесс MCP](../../mcp-board-workflow.md) и
  [контракт routing candidates](../../mcp-design.md#reviewed-builtin-routing).
- Архив [inputs.tar.gz](inputs.tar.gz) содержит самодостаточный проект
  `foilfern/ESP-PD-Sink.lpp`, исходные файлы KiCad `kicad/esp-pd.kicad_*`
  из `5b96caf` ветки `epr-48v`, и каталог `evidence/` с замерами,
  исходными отчётами и примерами BOM. Разверни архив в рабочий каталог
  облачной задачи и заведи отдельную копию для каждого применённого варианта.
- Собери MCP через `cargo build --locked -p librepcb-mcp --bin librepcb-mcp`.
  Если исходники upstream находятся вне `../LibrePCB`, укажи
  `LIBREPCB_UPSTREAM_DIR`. Для сборки нужен ресурс
  `share/librepcb/fontobene/newstroke.bene` из upstream. Сервер работает
  по stdio. Передай абсолютный путь через `--project` или открой копию
  инструментом `project_open`. Прогон через stdio-клиент подходит для
  облачной среды без GUI. Порядок работы описан в
  [руководстве Foilfern](../../mcp-board-workflow.md).
- Перепроверь `board_get`, `erc_run` и `drc_run`. База имеет
  86 посадочных мест, 0 разрывов, 0 ERC, 3 ошибки DRC и 9 предупреждений.
  Две ошибки относятся к зазору медь–отверстие у J2, третья к
  `AE1:2` в keepout. Предупреждения касаются восьми щелей и радиуса
  контура. In1 служит опорной землёй. Исходные отчёты Foilfern и
  LibrePCB 2.1.1 лежат в архиве.
- Цель предыдущего прохода состояла в замыкании цепей на импортированном
  размещении. Сначала разводились силовые цепи, земля, USB и RF. Из 86
  координат и сторон посадки поменялась только координата C11,
  с `(116.25, -117.10)` на `(116.25, -118.50)` мм. Результат
  служит базой для сравнения качества размещения.

## Порядок работы и приёмка

1. **OLED.** Перенеси исходную геометрию коротких веток KiCad или собери
   вариант с разворотом C21/C22 и малыми сдвигами. Сначала сократи
   VCOMH и OLED_VCC. Сравни сохранённые пути и via с базой, затем оцени
   RESET. Сохрани положение FPC и вырез. В архиве есть аргументы и
   отчёт первой отвергнутой пробы. Разворот обоих конденсаторов при
   исходных координатах дал конфликт C22.1 с via GND. Сдвиг C22
   только по X на 0,25 мм перенёс конфликт на соседнее via VCC.
2. **U5.** Отдельным кандидатом разведи FB по Top и сократи входную
   петлю. Затем оцени U2, Kelvin U6/R17 и ADC по таблице. Для сравнения
   используй прямое расстояние, длину дорожки, слои, ширину, число via
   и фактическое подключение возврата. Каждый локальный вариант
   проверяй относительно одной и той же базы.
3. **Проверка.** Готовый вариант должен иметь 0 разрывов, сохранённый
   netlist и 0 новых нарушений DRC. Укажи наследуемые и новые
   предупреждения по отдельности. Для RF и USB сравни фактические
   изменения и покрытие опорной землёй с исходным снимком. Проверь
   экспорт Gerber/Excellon и повторное открытие сохранённого проекта
   upstream LibrePCB, если CLI доступен. В отчёте укажи, какие
   электрические свойства ещё требуют моделирования или измерений.
4. **Результат.** Сохрани native-проект, рендеры обеих сторон, аргументы
   применённых кандидатов и таблицу до/после. Веди работу в ветке
   облачной задачи. Закоммить проверенные логические шаги и запушь их
   через доступный Git remote. Для изменений Rust используй
   целевые тесты затронутых крейтов по `AGENTS.md`.

## Скорость роутинга и проверок

Воспроизведи один локальный OLED-кандидат и один проход builtin на
фиксированном снимке. Измерь время и пиковую память при одинаковых
параметрах сборки. Разложи время на создание снимка, поиск маршрута,
восстановление связности, построение заливок и DRC. Замерь
`prepare`, `preview` и `apply` отдельно. Сохрани число поисков,
расширенных узлов и попыток rip-up, если эти счётчики доступны.

Код `RoutingJob::run` в `routing_service.rs` вызывает
`capture_routing_state` до и после изменений. `apply` проверяет
применённый результат ещё раз. Это начальные точки для профилирования.
Установи по измерениям, сколько занимает общий baseline, повторное
построение заливок и проверка после применения. Проверь, можно ли
переиспользовать результат для той же ревизии и платы, и измерь
ускорение. Сохрани защиту от устаревшей ревизии и проверку связности,
включая разрывы GND после локальных изменений.

Отдельно профилируй сам builtin. Сравни ограниченный поиск для одного
узла, объём перебора и повторные попытки на загруженной области.
Выбери узкое место по профилю. Для каждого ускорения сравни на одном
входе время, оставшиеся разрывы, новые DRC, число via и длину дорожек.
На итоговой плате сократи обходы и смены слоёв в проверяемых узлах
и сохрани эти же метрики до и после. Основные эксперименты запускай
в облаке. Переиспользуй сохранённые результаты и запускай тесты по
затронутым областям.

## Группы компонентов в Foilfern

Начни с машинно читаемых групп для ревью и выбора объектов. Группы
могут пересекаться. Например, R17 входит в силовой путь и в Kelvin-узел.
Поддержи стабильные ссылки на экземпляры компонентов и конкретные
выводы, чтобы переименование designator сохраняло связи. Для JSON
пользователю достаточно designator и имени вывода, которые Foilfern
разрешает при загрузке.

Поверх групп добавь направленные требования с источником и приоритетом.
Примеры для первого прототипа: расстояние между площадками, максимальная
длина пути, сторона монтажа, допустимые слои, число via, сохранение
опорной меди, фиксированное положение или разрешённая область.
Отчёт должен показывать измерение и причину, если проверка недоступна.
Порог берётся из подтверждённого требования проекта. Общие сети VCC/GND
сами по себе не определяют принадлежность конденсатора к микросхеме.

Варианты хранения: сначала проектный JSON рядом с `.lpp` для
воспроизводимого ревью без изменения формата LibrePCB, далее поддержка
этих же объектов в декларативном документе Foilfern. Автоматический вывод
групп из схемы годится для подсказок с подтверждением. Используй ручные
группы для сравнения OLED и U5 и предложи небольшой следующий шаг в API,
когда измеренные случаи покажут, какие поля реально нужны.

## BOM

Проблема `Package=N/A` в эксперименте ESP32-C3 воспроизведена. Вызов
`export_bom` без `board` создаёт BOM проекта и по контракту заполняет
`Package` как `N/A`. Передай имя платы из `board_get`.

```json
{"board": "default", "assembly_variant": "Std"}
```

На исходном проекте сравнения обе версии содержат 36 designator в
23 строках. В board BOM заполнены все корпуса. На ESP‑PD‑Sink board BOM
содержит 80 устанавливаемых позиций в 53 строках. C3, C31, R2, R7,
R26 и R28 отсутствуют в этой сборке. Пустые MPN и Manufacturer отражают
отсутствие заполненных закупочных данных. Для UX можно возвращать явный
scope и выбранную плату в ответе, сохраняя режим проекта.
